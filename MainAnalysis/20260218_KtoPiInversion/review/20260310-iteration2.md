# Reviewer Report

Author: Yen-Jie Lee and OpenAI

## Scope

This review checks the active code for places where runtime could be reduced by:

- in-process multithreading
- process-level parallel execution
- better separation between thread-local work and final reductions

The focus is on the main production chain in `20260218_KtoPiInversion`.

## Findings

### 1. High: the main event loop in `KtoPiAnalysis.cpp` is the highest-value parallelization target, but it is not thread-safe in its current form

Relevant files:

- `KtoPiAnalysis.cpp:736-1126`
- `KtoPiAnalysis.cpp:1031-1097`
- `KtoPiAnalysis.cpp:1108-1124`
- `KtoPiAnalysis.cpp:1178-1379`

What is happening:

- The code processes events one by one in a long serial loop.
- Each event is independent at the physics level.
- During that loop, the code directly updates shared ROOT histograms and shared accumulator arrays.

Why this matters:

- This is the dominant place where CPU time is likely spent.
- It is also the place with the largest potential speedup from multithreading.
- However, a naive OpenMP pragma or `std::thread` split would introduce data races immediately.

Specific thread-safety blockers:

- shared histogram fills in `hKPt`, `hPiPt`, `hPPt`, `hUPt`
- shared response histograms such as `hNtagResponse*` and `hDNdEtaResponse*`
- shared arrays such as `SumKAsK`, `SumPiAsPi`, `SumRecoEffK`, `CountEffTracks`, and related vectors
- shared messenger state via `M->GetEntry(ievt)`

Conclusion:

- This loop should be parallelized only with a thread-local accumulation model:
  - one reader or one messenger per worker
  - thread-local histograms and per-bin accumulators
  - one explicit reduction/merge step before the existing post-loop correction stage

### 2. High: `BuildDNdEtaResponse.cpp` is a simpler and safer first target for in-process multithreading

Relevant files:

- `BuildDNdEtaResponse.cpp:120-220`
- `BuildDNdEtaResponse.cpp:212-219`

What is happening:

- The code runs a serial event loop over the MC tree.
- The work done per event is independent.
- The only cross-event outputs are a small set of histograms filled at the end of each event.

Why this matters:

- This is structurally much simpler than `KtoPiAnalysis.cpp`.
- It has fewer shared accumulators and less correction logic.
- It is a better first multithreading target if the goal is to de-risk the implementation.

Recommended approach:

- split entries by range across workers
- give each worker its own local histogram set
- merge all local histograms at the end

Conclusion:

- If a first multithreaded implementation is desired, this file is the lowest-risk place to start.

### 3. Medium: the `dNch/deta` variation driver is still serial even though the jobs are independent

Relevant files:

- `run_systematics_dndeta_unfolding.py:206-215`
- `run_variations_20260306.sh:37-44`
- `analysis_mt.sh:20-27`

What is happening:

- `run_systematics_dndeta_unfolding.py` loops over each variation one at a time.
- For each variation, it runs the analysis and then the unfolding sequentially.
- The variation jobs are independent and do not require shared memory.

Why this matters:

- This is an easy wall-time optimization.
- The repository already uses process-level fan-out elsewhere with `xargs -P`.
- This can reduce turnaround time without touching the internals of the C++ event loop.

Conclusion:

- Before changing core C++ code, there is a straightforward speedup available by running variation workflows concurrently at the process level.

### 4. Medium: there are explicit thread-safety issues that must be addressed before adding multithreading to the C++ analysis code

Relevant files:

- `KtoPiAnalysis.cpp:126-144`
- `KtoPiAnalysis.cpp:727-744`
- `KtoPiAnalysis.cpp:738`

What is happening:

- `IsChargedPDG` uses a mutable static `unordered_map` cache.
- The progress bar writes to shared `cout` during the event loop.
- The active messenger object is advanced in place with `GetEntry`.

Why this matters:

- Even if histogram fills were made thread-local, these pieces would still be unsafe or noisy under multithreading.

Conclusion:

- The code needs a full thread-aware design, not just a loop pragma.
- At minimum:
  - remove or protect the mutable cache
  - disable or centralize progress reporting in threaded mode
  - avoid sharing one messenger object across worker threads

### 5. Low: the small Python and postprocessing loops are not the best place to spend threading effort first

Relevant files:

- `build_systematics_v3_with_unfolding.py:141-179`
- `build_systematics_v3_with_unfolding.py:371-399`
- `make_ptopi_results.py:218-230`
- `make_kpi_vs_dndeta_comparison_plots.py:216-262`

What is happening:

- These scripts do some repeated histogram cloning and per-bin calculations.
- The loops are serial, but the data volume is small.

Why this matters:

- These sections are unlikely to dominate runtime compared with reading full ROOT trees.
- Parallelizing them first would increase complexity with limited payoff.

Conclusion:

- The main return on effort is in event-level C++ processing and variation-level process concurrency, not these small postprocessing loops.

## Assumptions and limits of this review

- This is a static code review only. No profiling run was performed in this pass.
- Existing process-level parallelism in `analysis_mt.sh` and `run_variations_20260306.sh` was treated as already available.
- The review assumes the main runtime cost comes from ROOT event processing rather than note generation or plotting.

## Recommended next actions

1. If the goal is the fastest low-risk speedup, parallelize the variation workflow in `run_systematics_dndeta_unfolding.py`.
2. If the goal is the largest long-term speedup, redesign `KtoPiAnalysis.cpp` around thread-local event accumulators and a final reduction step.
3. Use `BuildDNdEtaResponse.cpp` as the first in-process multithreaded prototype before touching the larger analysis executable.
4. Reuse `validate_multithread_consistency.py` or an equivalent checker whenever multithreaded outputs are introduced.

## Overall review status

There are real opportunities to speed up the analysis, but the main event-processing code is not ready for naive multithreading.

The best opportunities are:

- process-level parallel execution of independent variation jobs
- a staged multithreading implementation starting with `BuildDNdEtaResponse.cpp`
- a later thread-local reduction design for `KtoPiAnalysis.cpp`

The main risk is correctness drift from race conditions if shared histograms, shared accumulators, and the shared tree messenger are not restructured first.

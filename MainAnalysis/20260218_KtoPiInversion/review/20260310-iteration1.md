## Findings

### 1. High: the final `N_tag` v3 central values are not being built from the unfolded Bayes result

Relevant files:

- `build_systematics_v3_with_unfolding.py:35-88`
- `run_systematics_checks.py:240-289`
- `runNtagUnfolding_BayesSVD.C:274-278`
- `overleaf_repo_git/main.tex:325-330`
- `output/systematics_20260306_v3/systematics_table_v3.txt:1-6`
- `output/systematics_20260306/systematics_table.txt:1-6`

What is happening:

- `build_systematics_v3_with_unfolding.py` reads `output/systematics_20260306/systematics_table.txt`.
- That upstream table is produced from reco-level `hKoverPiCorrected` double ratios in `run_systematics_checks.py`.
- The v3 builder rescales those reco-level values by closure and PID SF factors instead of starting from `hDataOverMcBayes`.

Why this is a problem:

- The note says the final `K/pi` ratio is formed on the unfolded true-`N_tag` axis.
- The generated v3 table does not match the actual unfolded Bayes output.
- This is not just a presentation issue. It changes the quoted final numbers.

Concrete example:

- `output/systematics_20260306_v3/systematics_table_v3.txt` bin 1 quotes `nominal = 0.383907`.
- The actual Bayes output in `output/NtagUnfolding_BayesSVD.root`, after applying the documented residual correction and PID SF factor, is about `0.544` for the same bin.

Conclusion:

- The current quoted `N_tag` v3 result is not the unfolded result described in the note.

### 2. High: statistical uncertainties for the Bayes `N_tag` result are lost during unfolding, and the final table substitutes reco-level errors

Relevant files:

- `runNtagUnfolding_BayesSVD.C:28-94`
- `runNtagUnfolding_BayesSVD.C:274-278`
- `build_systematics_v3_with_unfolding.py:67-84`
- `build_systematics_v3_with_unfolding.py:141-161`

What is happening:

- `IterativeBayesUnfold1D` in `runNtagUnfolding_BayesSVD.C` fills unfolded bin contents but does not assign bin errors.
- As a result, `hDataOverMcBayes` is written with zero statistical errors.
- The v3 builder then reuses `stat_raw` from the old reco-level table and rescales it.

Observed output behavior:

- In `output/NtagUnfolding_BayesSVD.root`, `hDataOverMcBayes` has zero bin errors in the first several bins.
- `hDataOverMcReco` and `hDataOverMcSVD` do carry nonzero uncertainties, so the loss is specific to the Bayes branch.

Why this is a problem:

- The final quoted statistical uncertainty is not the uncertainty of the unfolded Bayes result.
- The current table mixes Bayes-style central-value handling with reco-level statistical bars.

Conclusion:

- Even if the central-value issue above were fixed, the current Bayes `N_tag` final result still lacks a valid statistical treatment.

### 3. Medium: the residual-closure term mixes relative and absolute quantities

Relevant files:

- `overleaf_repo_git/main.tex:612-651`
- `build_systematics_v3_with_unfolding.py:71-84`
- `finalize_dndeta_systematics.py:115-131`

What is happening:

- The note defines the residual term as `delta_resid = 1/2 * |1/C_i - 1|`.
- That is a relative multiplicative offset.
- The implementation then adds it in quadrature with absolute bin shifts such as binning and unfolding variations.

Why this is a problem:

- The combination is only dimensionally consistent if the observable is implicitly normalized to 1.
- For bins away from unity, the residual term is not on the same scale as the other absolute uncertainties.

Impact:

- This affects both the `N_tag` v3 builder and the `dNch/deta` finalizer.
- The numerical size may still be small in many bins, but the definition is inconsistent.

Conclusion:

- The residual uncertainty should be defined either as a relative term everywhere or converted into an absolute uncertainty before quadrature.
